## 0. Verdict and top defects

The v4 record **shape** is strong (closed schema, frozen/live split, arithmetic vectors, deterministic id). The **contract seam** is not: the page is a self-contained record spec that no longer says who writes what, where records live, how they relate to today's documents/ids/statuses, or how historical picks are excluded. As written it would let a team build a schema-correct implementation that deadlocks on "who sets `awaiting_result` / `is_closing` / `outcome`", overwrites another sport's record (document id = `pick_id`), or backfills historical picks against the explicit product rule.

Blocking findings in one line each:

- **B1 Writer model broken.** §1 lists producers = bet engines + Publish Engine, consumers = BFF/monitor/settlement, yet Rule 5 makes monitor observations and settlement *writes* to the same record. The earlier edition's decisive sentence — "the Publish Engine is the only writer of pick documents" (`producers-to-bff.md:11,33`) — was dropped and is still the premise of KDD-001 (`kdds.md:42`) and its etag/merge guardrails (`kdds.md:32-35`).
- **B2 No writer/trigger for `current_*`, `observed_at`, `is_closing`, `awaiting_result`, `outcome`.** All five are contract-required live state; none is assigned. Today the monitor writes Firebase + watchlist + a Delta history table only (`live-odds/shared/firebase_writer.py:1-9`, `live-odds/nfl/mappers/poll_history.py:1-16`), settlement write-back is stubbed (`producers-to-bff.md:573`), and no producer emits `awaiting_result` (`app-data/databricks/publisher/canonical_transformations.py:42-46` has no such value).
- **B3 Merge/ordering semantics undefined.** Terminal-vs-observation precedence, monotonic `observed_at`, duplicate/re-run idempotency, re-issue counter `n`, frozen re-evaluation (`probability_moved`), AU mirroring and post-terminal retention are all unstated; they currently exist only in KDD-001 and a mock plan (`mock-records-plan.md:121-134`).
- **B4 Storage/id seam dropped but load-bearing.** The Store row naming KDD-001 (one record per document, `id = pick_id`, partition `/game_sk`) was removed (`producers-to-bff.md:14`; `kdds.md:27-35`). With `id = pick_id`, the dropped CI rule "`game_sk` must never be used by two sports … producer CI rejects it" (`producers-to-bff.md:254`) becomes a cross-sport overwrite risk, and KDD-001 still lists global key ranges as an open item (`kdds.md:148`).
- **B5 Historical-picks scope absent.** The page opens "Every Edge Pick is published as one strongly typed record" (`conf-schema-contracts.md:3`), which is false for pre-redesign picks and invites exactly the backfill/placeholder treatment Confluence v6 forbids. No scope/cutover/pin/“never convert legacy” statement exists (see §3.3). Verdict: **no new vintage field is needed** — `schema_version` + container + record existence are sufficient — but the contract must say so and must scope Rule 2 so persistence cannot be read as a backfill mandate.
- **B6 Derived values are computed in at least three places and can disagree.** The record stores `entry_edge`/`current_edge`/`edge_status` on the producer's basis; the snapshot API recomputes `entry.edge`/`current.edge`/`edge_state` on an EV display basis (`bff-to-app-contract.md:94,100,187-206`); the overlay recomputes `live_edge`/`edge_status` (`realtime-overlays.md:70-98`); the v7 BFF plan recomputes and reports `edge_state_mismatch` (`option-b-plan.md:304`). The contract's "single source of truth" claim (`:3`) is therefore not what consumers do.
- **B7 `rec_action` can never be populated in 4.x, but the redesign requires Recommended Action.** §6.4 #34 says "reserved for `play`, `watch`, `pass`" but the schema types it `null`; the product requirement asks for "Rec. Action (Play, Watch, Pass) based on current edge" (Confluence v6, Backend §5 / Front End §5). Probe: `rec_action: "play"` fails validation; §2.6 would call that a major change. This is the one redesign requirement the v4 contract structurally blocks.
- **B8 Status/outcome crosswalk dropped, and another doc cites it.** The earlier edition's "Values the BFF accepts until producers write this page's statuses" table (`producers-to-bff.md:578-590`) was removed in the new edition, but KDD-003's legacy mapping table points at it by name (`kdds.md:396`). Teams have no sanctioned mapping from today's values (`scheduled/active/pending/won/lost/push/void/cancelled/rescheduled/abandoned`, `bet_outcome` 0/1/2, Format A statuses) to the v4 enum.
- **B9 Consumer-side seams the record does not close:** bookmaker display name (record has slug only), `stat_code`→display label registry (the BFF's `STAT_NAME_BY_ID` map has nine NBA codes only — `mobile-server/src/lib/constants.ts:56-66`), AU source rule (`market_average` vs record `odds_source_kind`), and the record has no game start time, so `is_closing`/`awaiting_result` derivation always needs the schedule join (undefined).

### 1.4 Unassigned write paths (findings)

- **W1 — `current_*` + `observed_at` + `is_closing`.** Contract requires them; no writer named. KDD-001 implies "monitor → Delta history → PE merge → record", but the record contract (the thing every team builds against) never says it. Earlier edition said so explicitly; regression.
- **W2 — `awaiting_result`.** No trigger. The state diagram annotates the transition "(Game starts (is_closing = true))" (`:75`), but a record can be schema-valid in `awaiting_result` with no observation at all (probe below, I2). Who watches the schedule to move `open → awaiting_result`? PE would need to join the schedule on `game_sk`; the record carries no start time (see §2.1 F4).
- **W3 — `outcome` / settled / void.** Settlement is listed as a consumer; Rule 5 makes it a writer; §4.2 says it is "evaluated against the frozen entry selection and line" but not by whom. Today nothing writes it. Without an owner, the record can never leave `awaiting_result`; the snapshot contract only terminates on settled/void (`bff-to-app-contract.md:152-153`).
- **W4 — persistence mechanism.** Rule 2 says a producer must transition a pick it stops backing; but engines rebuild picks each run (today's behaviour, `producers-to-bff.md:568-569,601`) and the only "open" item about it was dropped from the new edition. Who compares a run's output with the store and emits the cancellation? If PE infers cancellation from absence, a partial run cancels real picks; if the engine must emit it, the engine needs a previous-output read and a signed cancellation row. Undefined either way. `mock-records-plan.md:121-134` proves this logic currently lives only in a mock plan.
- **W5 — re-issue counter.** §8.2/§8.4 make `n` a parameter of `build_pick_id(record, team_slot, reissue)`, but `n` is not on the record and not derivable from record + schedule. §9.1 invariant 1 ("Rebuilding `pick_id` from the record's fields and the game schedule … yields the exact `pick_id`") is therefore unsatisfiable for any `|r2+` record. The counter needs an explicit rule (1 + highest prior re-issue for the same selection/region) and a state owner (PE store scan).
- **W6 — duplicate recommendation while the previous pick is still `open`.** Rule 1 only covers re-issue after `cancelled`/`withdrawn`; a rebuild that re-recommends the same selection+line while it is open must be the same record (idempotent upsert by `pick_id`), but the contract doesn't say so. Today's engines rebuild every run, so this is the normal case, not an edge case.
- **W7 — AU records.** Rule 1 requires one record per region; today the NBA engine copies the US pick into AU (`producers-to-bff.md:568`; `kdds.md:266`). Nobody is named to mint the AU record, decide whether AU entry odds/stake are independent, or decide what `odds_source_kind`/`entry_bookmaker_id` mean when the AU price is a US book (see F3). KDD-002 lists "au picks: NBA copies the us pick into au → au has its own picks" as a behaviour change needing product confirmation (`kdds.md:266`); the contract asserts region-scoped records without stating the transition rule.
- **W8 — `pick_date_time` on first publish.** Frozen "timestamp when the pick was first published" (`:212`). Which publication — engine table emission or PE Cosmos write? KDD-001's merge means PE can write hours after the engine produced the row. Needs a one-line definition (engine recommendation time, carried frozen through the merge).

### 1.5 Single-writer conflicts

- **W9 — Contract vs KDD-001.** KDD-001's whole design ("etag guard keeps two writes from overwriting each other", `kdds.md:33,61`) presumes one writer process; the contract now names bet engines as producers and three systems as record updaters. If any of the five engines or the monitor were later allowed to write Cosmos (the natural reading of "producers"), the etag design, the schema-validation guardrail and Rule 3's immutability guarantees all fail. The contract must state **single writer = Publish Engine** and model engines/monitor/settlement as *value sources feeding the writer*.
- **W10 — Monitor as direct writer.** The overlay contract has the monitor write Firebase nodes keyed from `pick_id` (`realtime-overlays.md:44-64`) and delete them when the pick stops being open (`:49`); it also computes `edge_status` itself (`:70,82-98`). If the monitor also wrote the record, two writers would race the settlement write. The earlier edition's "never by a direct write" (`producers-to-bff.md:33`) exists precisely to prevent this; it was dropped.
- **W11 — Settlement vs cancellation terminal-state race.** Both can be the first terminal write after the game. Rule 6 forbids moving backwards; there is no stated precedence when a cancelled pick later has a result (delivery-options flags exactly this unresolved grading case, `delivery-options.md:155`). The record would keep `cancelled` + `outcome=null` forever, so My Picks cannot grade it.

## 3. Versioning / coexistence / Historical Edge Picks

### 3.1 Three generations live in the same estate

| Generation | Where | Shape | `schema_version` | Id | Status vocabulary |
| --- | --- | --- | --- | --- | --- |
| NBA 2026 canonical (Format B) | `c-wltp-*`, `c-ps-*` | per-game doc, region map / team-slot nested picks | `1.00` (picks), `1.10`, `2.0.0` | doc `{league}\|{doc_type}\|{game_sk}`; pick `id` inside | `scheduled…abandoned` |
| Format A legacy (NFL/MLB/WNBA/EPL) | `c-wltp`, `c-ps`, `game_prediction.top_picks` | one pick per region in `top_picks`; `type`, `code`, `bookmaker.position` | none / legacy | `{game_sk}_{bet_type}_{region}` | mixed case; `bet_outcome` 0/1/2 |
| v4 producer record | **new container** (KDD-001, `kdds.md:27`), not yet created | one record per pick per region | `4.x.y` | `pick_id` (also doc id) | `open…withdrawn` |

The contract covers only the third. It must say that explicitly: (a) the 37-field schema validates **only** v4 records, never a canonical or Format A document; (b) the two families coexist by container/route, not by `doc_type` (the record has no `doc_type`); (c) no reader may guess the family from field presence — a v4 record is closed and all-present.

One schema cannot cover both: the canonical docs are per-game with nested arrays and envelope fields (`doc_type`, `league`, `season`, `taxonomy_version`, `publish`), and their `pick_status`/`edge`/`bookmaker` semantics differ. Trying to extend the 37-field closed schema to legacy docs would break `additionalProperties:false` and both consumers. The earlier edition's note — the schema validates the record, the PE adds the Cosmos `id`, a reader strips Cosmos fields (`id`, `_*`) before validating (`producers-to-bff.md:299`) — was dropped; restore it or the `additionalProperties:false` vs mandatory Cosmos `id` contradiction is live again (that was KDD-feedback finding 2.1, `kdds_feedback.md:25-39`).

### 3.2 Is a redesign/vintage/cut-off field needed on the record?

**No — if, and only if, the contract states the scope rules below.** The consumer-side decision already exists: KDD-003 gives every pick `era: legacy|v4` and the app draws the card from `era`, never from which fields are null (`kdds.md:343-357`); kdd23 amends era resolution to "v4 iff the league switch is on and the record store has ≥1 record for (region, game_sk)", so the BFF reads the producer's decision from data, not config (`kdd23-design.md:124-140`); delivery-options records that this era-by-record-existence is why option B was chosen ("no producer record means `era: legacy`", `delivery-options.md:95`). Adding a `vintage`/`redesign` field would itself be a new data point for old picks and would duplicate `era`. `schema_version` is sufficient *as a contract-version marker*; it is not, and must not become, an era/cut-off marker (legacy docs already use `1.00/1.10/2.0.0`).

But the producer contract currently undercuts that design in several ways:

- **H1 — Overbroad scope sentence.** "Every Edge Pick is published as one strongly typed record" (`:3`) is false for historical picks. It reads as a universal obligation. Rewrite to: "Every pick **first published in a game pinned to v4** (league cutover) is published as …; picks published before a league's cutover keep the legacy documents and are never converted, backfilled or re-expressed in this shape."
- **H2 — Rule 2 must not imply backfill.** "Once a pick record is published, it must remain present in every subsequent publish…" plus the 37-field all-present rule could be implemented by minting records for old picks. Add: "Rule 2 applies only to records created after the cutover; a record is never created for a pick whose legacy document already exists. Historical picks get no placeholder values and no recomputation."
- **H3 — Retaining terminal records (I6/M8).** Required for historical results and the track record; fix the retention window.
- **H4 — Cutover boundary.** The product requirement cuts off **by publish date** ("picks published on or after [release date] use the new design; earlier picks use the original design", Confluence v6 Historical block). KDD-002 point 5 cuts over **by game start** ("games that start on or after its v4 start date are published as producer pick records", `kdds.md:181`). Those disagree for games straddling the cutover (picks already published by the old pipeline for a game after the date). The corpus needs one rule; the safest and requirement-compliant one is the first-publish pin already listed as a KDD-002 prerequisite (`delivery-options.md:47`: "pinning a game's family at first publish"), i.e. **a pick's family is fixed at its first publish**; the producer contract should state it and that games are not re-homed. kdd23's era-by-record-existence is then consistent: old picks have no records → legacy.
- **H5 — "Show exactly as published, no blank or placeholder fields".** v4's "all 37 fields present, null means not applicable" is a *record* convention; it must not be applied to historical picks. State that the consumer contract's `era`/limited-card rules govern display, and that no default, zero, placeholder or recalculated v4 value is written for a legacy pick. Note a corpus-level risk the Lead should carry: KDD-003 maps legacy picks and **recomputes `entry.edge` on the v4 display basis** (`kdds.md:394`) — that is a recalculation, which the requirement says will not be done. KDD-003 itself flags "whether legacy picks show an edge at all" as open (`kdds.md:428-431`); it must be resolved as product copy/behaviour before the contract set is agreed, not silently shipped.
- **H6 — Consumer contracts must carry the signal.** The requirement is only satisfiable if the app receives an explicit era and does not infer it from nulls. `bff-to-app-contract.md` (Oct 19) has **no `era` field and no historical section**; KDD-003 (Oct 20) says it adds `era`, and the decided option-B plan puts `era` in the v7 block (`option-b-plan.md:162,203,413`). The producer contract should cross-reference KDD-002/003/delivery-options and state that `era` lives on the consumer side, so a producer cannot accidentally mint it.
- **H7 — Vocabulary/semantic stability for old picks.** The v4 formula normalizes milestone props (`k−0.5`, `player_over`) and alternate variants (`main`), and its id pattern rejects today's milestone/alternate/Format A ids (`option-b-plan.md:246`). Historical picks must keep their legacy ids (opened slips/follows already point at them — KDD-002 point 8, `kdds.md:190`). Contract must state: published ids are never rewritten; the new formula applies only to new v4 records; historical ids are out of scope.

### 3.3 Verdict

- Record needs **no** `vintage`/`redesign`/`cutoff` field: `schema_version` 4.x + separate container + "record exists" is sufficient for the consumer's `era`.
- Contract **does** need an explicit scope/coexistence section (H1–H7): what exists before cutover, that it is never backfilled/relabelled, that terminal records are retained, that the cutover is pinned at first publish per game/league, and that `era` is a consumer field not inferred from nulls. Without it, the page fails the Historical Edge Picks requirement in practice even though the schema itself is fine.
